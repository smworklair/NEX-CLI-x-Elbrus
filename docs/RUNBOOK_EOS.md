# Прогон на Kaggle: изолируем EOS, потом добавляем данные

Порядок здесь важнее команд. Меняются две вещи сразу — модель впервые видит
EOS и впервые получает вдвое больше данных. Если запустить одним прогоном,
прирост будет, а объяснения не будет.

## Что уже установлено локально

| факт | как проверено |
|---|---|
| Профиль генератора == `vliw/core/model.py` | посимвольная сверка всех таблиц, расхождений 0 |
| 40 000 примеров законны, разрыв до оптимума 0 | `Schedule.validate()` из `vliw.core`, оба файла |
| Утечки эвала в обучение нет | пересечение промптов = 0 по всем парам файлов |
| Адаптер обучался БЕЗ EOS | архивный `training/checkpoints/train_qlora.py`: `text = prompt + "\n" + completion` |
| 75% ошибок — чистая неостановка | пересчёт `eval_kinds.jsonl` текущим `classify()`: 24 «хвоста» из 32 ошибок |

## Что заливать в Kaggle

Как Dataset (Input):

```
train_merged.jsonl              39 700 примеров, 24 МБ  — обучение прогона 2
dataset.jsonl                   20 000 — обучение прогона 1 (те же данные, что и раньше)
eval.jsonl                         300 — старый эвал, графы 6..14, для «до/после»
eval_wide.jsonl                    300 — held-out 4..24, покрывает крупные графы
```

Через `%%writefile` в ячейки: `train_qlora.py`, `validate_kaggle.py`.

Старый адаптер `qwen-vliw-lora` нужен как Input — он и baseline, и стартовая
точка прогона 1. **Не перезаписывать:** у всех запусков `--out` свой.

## Шаг 0. Baseline тем же классификатором

Без этого шага сравнивать не с чем. Цифра «36% валидно» снята дампом от
15.08 22:40, а `validate_kaggle.py` переписан в 22:51 — прежний классификатор
не отделял «хвост» от «галлюцинации» и записал 24 законных префикса в
безнадёжные. Нужен замер текущим кодом, иначе прирост будет частично
бумажным.

Обучения здесь нет, только генерация — дёшево.

## Шаг 1. Изолированный EOS: одна переменная

Данные ТЕ ЖЕ, что и в прошлом обучении (`dataset.jsonl`), продолжаем
существующий адаптер, одна эпоха. Отличие от прошлого раза ровно одно — EOS.

```bash
!python train_qlora.py \
    --base Qwen/Qwen2.5-3B-Instruct \
    --adapter /kaggle/input/vliw-lora/qwen-vliw-lora \
    --data /kaggle/input/vliw-data/dataset.jsonl \
    --out /kaggle/working/lora-eos \
    --epochs 1
```

В первых строках лога обязана появиться самопроверка:

```
EOS в конце каждого примера: '<|im_end|>'
  последний токен примера: 151645 '<|im_end|>' (eos_token_id=151645, pad_token_id=151643)
  EOS попадает в loss (labels != -100) — ОК
```

Если вместо этого напечатано `!! ВНИМАНИЕ` — прогон останавливать, дальше
смысла нет. Ради этих трёх строк всё и затевалось.

Замер:

```bash
!python validate_kaggle.py --model /kaggle/working/lora-eos \
    --dump /kaggle/working/eos_eval.jsonl \
    /kaggle/input/vliw-data/eval.jsonl
```

```bash
!python validate_kaggle.py --model /kaggle/working/lora-eos \
    --dump /kaggle/working/eos_eval_wide.jsonl \
    /kaggle/input/vliw-data/eval_wide.jsonl
```

Второй замер — инференс на 300 примерах, обучения нет, стоит копейки. Нужен,
чтобы в таблице не было дырки: без него не отделить «EOS помог и на крупных
графах тоже» от «крупные графы вытянули новые данные».

**Что это докажет.** Если «хвост» схлопнулся к нулю, а «валидно» уехало к
80% — диагноз подтверждён полностью, и это результат одной строки, а не
20 000 новых примеров. Если хвост остался — значит одной эпохи мало либо
дело не только в EOS, и прогон 2 надо планировать иначе.

Потолок здесь 84% (столько сейчас законных префиксов) и это гипотеза, а не
обещание: доучивание может слегка сдвинуть и «сдвиг» с «ресурсом» — в любую
сторону.

## Шаг 2. Полный прогон на слитых данных

С нуля от базы, а не поверх старого адаптера: в нём запечена привычка не
останавливаться, переучиваться ей дороже, чем учиться с чистого листа.

```bash
!python train_qlora.py \
    --base Qwen/Qwen2.5-3B-Instruct \
    --data /kaggle/input/vliw-data/train_merged.jsonl \
    --out /kaggle/working/lora-merged \
    --epochs 2
```

≈ 4960 шагов при batch 4 × accum 4. Чекпоинты каждые 100 шагов — сессия
Kaggle уже обрывалась на 93% эпохи, поэтому `save_strategy="steps"`.

Замер по обоим эвалам:

```bash
!python validate_kaggle.py --model /kaggle/working/lora-merged \
    --dump /kaggle/working/merged_eval.jsonl \
    /kaggle/input/vliw-data/eval.jsonl
```

```bash
!python validate_kaggle.py --model /kaggle/working/lora-merged \
    --dump /kaggle/working/merged_eval_wide.jsonl \
    /kaggle/input/vliw-data/eval_wide.jsonl
```

## Итоговая таблица

Шесть дампов забрать с Kaggle и положить в `training/checkpoints/` под теми
именами, что стоят в командах выше. Дальше — локально, без GPU:

```bash
python tools/report_runs.py
```

Скрипт сам найдёт файлы по именам, напечатает состав ошибок по каждому
дампу, сводную таблицу и разбивку широкого эвала по размеру графа:

| прогон | eval.jsonl (6..14) | eval_wide.jsonl (4..24) |
|---|---|---|
| 0. текущий адаптер (без EOS) | | |
| 1. + EOS, старые данные | | |
| 2. + EOS, слитые данные, с нуля | | |

Строка 0 → 1 отвечает «сколько стоил EOS-баг».
Строка 1 → 2 отвечает «сколько стоили новые данные».
Колонка `eval_wide` отвечает «а что на графах, которых раньше не было».

**Важно:** `report_runs.py` пересчитывает ярлыки заново текущим
`classify()`, а не берёт `kind` из дампа. Дамп от 15.08 записан версией,
путавшей «хвост» с «галлюцинацией»; при сведении в одну таблицу с ярлыками
как есть 24 законных префикса ушли бы в брак и разница получилась бы
раздутой. Скрипт печатает, сколько записей переклассифицировал и во что.
