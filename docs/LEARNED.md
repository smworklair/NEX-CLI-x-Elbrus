# Как запустить обученные веса локально

До этого адаптер работал только на Kaggle: инференс жил в
`training/validate_kaggle.py`, самодостаточном РАДИ Kaggle, и умел ровно одно —
прогнать эвал по файлу. Из инструмента веса было не запустить вообще.

Теперь есть команда:

```bash
python -m vliw learned
```

Работает на обычном ноутбуке без GPU: ~30 секунд на граф. Если окружение не
поднято — не падает, а печатает, чего именно не хватает.

Поднять окружение с нуля: `tools/setup_local_llm.sh` (см. путь 2 ниже —
он основной).

## Что где лежит

| путь | что это |
|---|---|
| `training/checkpoints/qwen-vliw-lora/` | адаптер прогона 0 — обучен БЕЗ EOS, не останавливается |
| `training/checkpoints/lora-eos/` | адаптер прогона 1 — с EOS, 97.7% на узком эвале |
| `vliw/learned/runtime.py` | поиск весов, зависимости, загрузка, генерация |
| `vliw/learned/scheduler.py` | протокол `Scheduler`: граф → расписание |

Адаптеры — LoRA (r=16) поверх `Qwen/Qwen2.5-3B-Instruct`, по 120 МБ.
Сама база в репозитории не лежит и лежать не будет: её тянут с Hugging Face.

**Адаптеры — тоже.** Они опубликованы там же:
[`Shmonika/nex-vliw-lora`](https://huggingface.co/Shmonika/nex-vliw-lora) —
три штуки в `safetensors` и они же в готовом GGUF. В git они не идут по той
же причине, что и база: 120 МБ на файл, а GitHub блокирует всё крупнее 100 МБ.

Раньше их не было нигде, кроме машины автора, и это была настоящая дыра:
`tools/setup_local_llm.sh` искал адаптеры в `training/checkpoints/` — папке,
которая у скачавшего репозиторий пустая. База качалась, движок ставился, а
обученной модели не появлялось. Человек получал чистую Qwen без единого шага
обучения этого проекта и не имел способа узнать, что это не та модель.

Всё, что качается и генерируется локально, живёт в `vendor/` и в git не идёт
(размер, а не секретность): движок llama.cpp, квантованная база и адаптеры в
GGUF. Восстанавливается `tools/setup_local_llm.sh` одной командой.

БАЗУ МЕНЯТЬ НЕЛЬЗЯ. LoRA — это выученная поправка к весам конкретного
чекпоинта, а не самостоятельная модель. Qwen3 не подойдёт (нет размера 3B —
формы матриц не сойдутся, упадёт при загрузке), Qwen2.5-Coder-3B опаснее:
формы совпадут, загрузится без ошибки и будет тихо выдавать чушь. Квантование
базы менять можно — это то же самое число, записанное грубее.

Тонкость: у `lora-eos` рядом НЕТ файлов токенизатора (обучение сохранило
только адаптер). Загрузчик это учитывает и берёт токенизатор у базовой
модели — руками ничего копировать не нужно.

## Путь 1: transformers (эталонный)

Тот же код, что гонялся на Kaggle. Работает как есть, если хватает памяти.

```bash
.venv/bin/pip install torch transformers peft
python -m vliw learned
```

Сколько нужно памяти (3.09B параметров):

| формат | вес модели | где разумно |
|---|---|---|
| float32 | 12.4 ГБ | практически нигде |
| bfloat16 | 6.2 ГБ | CPU от 16 ГБ ОЗУ |
| float16 | 6.2 ГБ | GPU (так гоняли на Kaggle) |
| 4-битный GGUF | ~2.0 ГБ | CPU от 8 ГБ — см. путь 2 |

Умолчания выставлены сами: на GPU — `float16`, на CPU — `bfloat16`
(`float32` не берётся никогда, а `float16` на CPU в torch местами не имеет
ядер). Переопределить устройство: `NEX_LEARNED_DEVICE=cpu`.

**На машине, где это писалось (7.5 ГБ ОЗУ, без GPU), путь 1 не годится:**
6.2 ГБ весов при ~5 ГБ свободных уйдут в своп, и один граф будет считаться
минутами. Команда об этом честно предупреждает до запуска.

## Путь 2: GGUF через llama.cpp — ОСНОВНОЙ на CPU

Это то, что реально работает на ноутбуке без GPU, и то, что выбирается по
умолчанию. База в 4 битах занимает 2.1 ГБ вместо 6.2 ГБ, и llama.cpp считает
на процессоре быстрее, чем torch.

Поднимается одной командой:

```bash
tools/setup_local_llm.sh          # движок + база + конвертация адаптеров
tools/setup_local_llm.sh check    # только проверить, что уже есть
```

Что она делает и почему именно так:

1. **Движок** — берётся ГОТОВЫЙ бинарник `llama-completion` из релизов
   ggml-org (17 МБ). Не `llama-cpp-python`: у него нет колёс ни под какой
   Python, он собирается из исходников, а компилятора (`cmake`, `g++`) на
   машине может не быть, и поставить их без root нельзя.
2. **База** — `qwen2.5-3b-instruct-q4_k_m.gguf` (2.1 ГБ) с Hugging Face.
   Единственная тяжёлая загрузка.
3. **Исходники llama.cpp** — только ради `convert_lora_to_gguf.py`: он
   импортирует пакет `conversion/`, по отдельным файлам его не собрать.
4. **Конвертация адаптеров** в GGUF. Ключ `--base-model-id`, а НЕ `--base`:
   первый берёт с Hugging Face только config базы, второй ждёт локальную
   папку с весами и падает с `FileNotFoundError: 'Qwen/Qwen2.5-3B-Instruct'`.

Две тонкости, на которых это ломается молча:

* **`-no-cnv` обязателен.** Иначе llama.cpp видит chat-шаблон в модели и
  оборачивает промпт в `<|im_start|>…`. Обучение шло на СЫРОМ промпте
  (`tok(row["prompt"])` в `validate_kaggle.py`), и с шаблоном модель получает
  не тот текст, на котором училась.
* **Эхо промпта надо срезать.** llama.cpp печатает промпт перед ответом, а
  парсер расписания намеренно терпимый — он примет строки графа за
  расписание, если их не убрать.

Ещё одна деталь окружения: бинарнику нужна `libgomp.so.1`, которой в системе
может не быть. Она лежит внутри установленного `torch` (`torch/lib/`), оттуда
и берётся через `LD_LIBRARY_PATH` — ставить её через apt не требуется.

**Контекст ограничен явно (`-c`), и это не мелочь.** Без этого флага llama.cpp
резервирует под KV-cache столько, сколько заявляет модель — у Qwen2.5 это
32768 токенов, хотя промпту и ответу вместе редко нужно больше 1000. Разница
измерена: 4.66 ГБ пиковой памяти с дефолтным контекстом против 3.59 ГБ с
ограничением под фактическую длину. Найдено не в теории, а по факту: полный
TUI держит в памяти кэш расписаний и отрисовку, и на этом запасе OOM-killer
убил подпроцесс модели прямо посреди `/learned` — `dmesg` показал `Killed
process … (llama-completio) anon-rss:1501892kB`. Экономия в мегабайт триста
как раз и есть разница между «убьёт» и «отработает».

### Что получилось на замере

15 примеров из `eval_wide.jsonl`, адаптер `lora-eos`, локально на CPU:

| | локально (GGUF Q4_K_M) | Kaggle (bnb NF4) |
|---|---|---|
| валидно | 27% | 32.7% |
| разрыв до оптимума | 0.00 такта | 0.02 такта |

Расхождение в 5 п.п. — от разного способа квантования базы, не от разных
весов адаптера. Это ожидаемо и заранее оговорено.

Важнее состав ошибок: **все 11 провалов из 15 — STORE, поставленный на канал,
который его не исполняет.** Локальный прогон один в один воспроизвёл диагноз,
снятый по дампам Kaggle (см. `docs/ROADMAP.md`): в `dataset.jsonl` не было ни
одной операции STORE, модель её просто никогда не видела. А те 4 примера, что
прошли, попали ТОЧНО в оптимум CP-SAT — когда модель не путает канал,
планирует она безошибочно.

Скорость: ~11 токенов/с, около 27–30 секунд на граф из 13–20 инструкций.

## Что показывает команда

`/learned` печатает не только результат, но и то, как модель ошиблась, —
потому что ошибается она часто, и это измеряемый факт, а не сбой инструмента.

Отличие от `baseline` и `oracle` принципиальное. Те по построению выдают
ЗАКОННОЕ расписание: нарушение означало бы ошибку в коде, и ядро на этом
намеренно падает. Обученная модель может поставить операцию на канал, который
её не исполняет, потерять инструкцию или не остановиться — на широком эвале
прогона 1 законных расписаний было 33%. Поэтому её результат:

* **не попадает** в общий кэш `Session.results()` — там контракт другой;
* **не объявляет** оптимальность (`optimal=None`): модель ничего не доказывает;
* несёт разбор в `notes` и `search_stats` — что не размещено, что дописано
  сверх графа, какие правила нарушены.

Сырой ответ модели, буквально: `/learned --raw`.

### Починка каналов (включена по умолчанию)

Замер дал ровное разделение: когда модель не путает канал, она попадает ТОЧНО
в оптимум. Когда путает — это почти всегда STORE, которого в её обучающих
данных не было ни одного. То есть ошибается она не в ПЛАНИРОВАНИИ, а в знании
матрицы машины, а матрица известна точно.

Поэтому такты модели остаются нетронутыми, а незаконный канал переназначается
на законный (`vliw/learned/repair.py`). Это не подгонка метрики: makespan
определяется тактами, а такты не двигаются вообще — закреплено тестом.

Раздача каналов — двудольное паросочетание, как в точном поиске. Жадный
«первый свободный» здесь ломается: ADD исполним на всех шести каналах и может
занять `,2`, оставив STORE (которому доступны только `,2` и `,5`) без места,
хотя решение существовало.

Результат подписан честно: «РАСПИСАНИЕ ЗАКОННО (модель + починка каналов)»
против «(чистый ответ модели)», и печатается, какие каналы переставлены.
Выключить: `/learned --pure`.

### Best-of-N: несколько сэмплов вместо одного

```bash
python -m vliw learned --bench 15 --best-of 4 --temperature 0.7
```

ЧТО ЭТО. При `temperature > 0` модель каждый раз отвечает чуть иначе, и на
один граф берётся N ответов. Каждый сэмпл идёт через тот же конвейер, что и
обычный ответ — включая починку каналов, — а побеждает кандидат с меньшим
числом нарушений `Schedule.validate()`; при равенстве — с меньшим makespan.
Сэмпл k получает seed+k: одинаковый seed на все попытки дал бы N одинаковых
ответов, а отсутствие seed — невоспроизводимый замер.

Умолчание не тронуто: без `--best-of`/`--temperature` генерация остаётся
жадной (`temperature=0`) — той же, что на всех замерах выше. На уровне
бэкендов это ровно прежний вызов: kwargs сэмплинга передаются вниз только
когда их реально просили (см. `sampling_kwargs()` в runtime.py), поэтому
поведение по умолчанию закреплено тестом байт-в-байт.

ЧЕСТНАЯ ГРАНИЦА. Это не «модель стала умнее»: best-of покупает валидность
генерациями, по N ответов на граф. Для протокола «один запрос — один ответ»
результат остаётся прежним.

### Замер: помогает ли best-of там, где repair не дотягивает

Починка каналов закрывает не всё: если модель нарушила зависимость
(потребитель раньше производителя) или заняла порт во времени — не двигая
такты, это починить нельзя, и `repair()` честно не пытается (см. его
докстринг). Вопрос замера: спасает ли другой сэмпл там, где первый законно
не чинится.

Прогон: 75 графов (каждый 4-й из `eval_wide.jsonl` — полный файл это сутки
на температуру), адаптер `lora-eos`, repair включён, N=8 при
t=0.4/0.7/1.0, seed=1. Прогон с N=8 закрывает и k=1,2,4 — это те же сэмплы,
усечённые до первых k. Инструмент: `tools/bench_bestof.py` (дампает каждую
строку в `build/bestof/*.json`, сводка — `bench_bestof.py summary`).

Доля валидных расписаний (75 графов):

| прогон | best-of-1 | best-of-2 | best-of-4 | best-of-8 |
|---|---|---|---|---|
| baseline (t=0, жадный) | **51/75 (68%)** | | | |
| t=0.4 | 47/75 (63%) | 53/75 (71%) | 54/75 (72%) | 55/75 (73%) |
| t=0.7 | 42/75 (56%) | 54/75 (72%) | 56/75 (75%) | **59/75 (79%)** |
| t=1.0 | 43/75 (57%) | 51/75 (68%) | 54/75 (72%) | 57/75 (76%) |

Средний разрыв до оптимума среди валидных (такты):

| t | k=1 | k=2 | k=4 | k=8 |
|---|---|---|---|---|
| 0.4 | 1.68 | 1.55 | 1.54 | 1.51 |
| 0.7 | 1.55 | 1.50 | 1.50 | **1.44** |
| 1.0 | 1.63 | 1.57 | 1.46 | 1.46 |

ЧТО ИЗ ЭТОГО ЧИТАЕТСЯ.

**Один сэмпл при температуре ХУЖЕ жадного** — 42-47 против 51. Это не
парадокс и не ошибка замера: температура добавляет шум, и одиночный
зашумлённый ответ проигрывает детерминированному. Весь выигрыш даёт
именно ВЫБОР, а не сэмплинг сам по себе.

**Выигрыш есть и он не мал**: 68% → 79% при t=0.7 и восьми сэмплах, плюс
разрыв до оптимума 1.55 → 1.44 такта. Обучения не потребовалось вообще.

**Половина выигрыша приходит уже на двух сэмплах** (68% → 72%), дальше
отдача падает. Если генерация дорога, k=2 берёт большую часть за четверть
цены.

**Температура 0.7 лучше и 0.4, и 1.0** на всех k. При 0.4 сэмплы слишком
похожи друг на друга (выбирать не из чего), при 1.0 шума столько, что
хорошие ответы встречаются реже: доля валидных ОДИНОЧНЫХ сэмплов падает
68% → 66% → 64% с ростом температуры, а выбор это компенсирует не
полностью.

ЦЕНА. best-of-8 — это восемь генераций на граф, то есть ~4 минуты на граф
локально против ~30 секунд. Для протокола «один запрос — один ответ»
верна строка baseline, а не 79%.

### Модель третьей колонкой в `/compare`

```bash
python -m vliw compare --model
```

Показывает решётки baseline, oracle и модели на одном графе, а внизу — три
makespan рядом. Без флага `/compare` остаётся мгновенным (0.3 с): модель
считается полминуты и по умолчанию не подмешивается.

### Стриминг

Строки расписания печатаются по мере генерации — первый символ через ~5 с
вместо тишины на все 30. Тонкость: llama.cpp сперва повторяет промпт и только
потом пишет своё, поэтому наружу отдаётся лишь то, что после эха (отсекается
по хвосту промпта в 40 символов); иначе в поток полезли бы строки графа, а
парсер расписания намеренно терпимый и принял бы их за ответ.

## Формат промпта — один на обучение и на запуск

`vliw/learned/scheduler.py` собирает промпт функцией `encode_prompt()` из
`training/encode.py` — тем же кодом, которым собирался обучающий датасет.
Продублировать формат «чтобы не тянуть training из vliw» было бы ошибкой:
вторая копия однажды молча разъедется с обучением, и модель начнёт получать
не тот текст, на котором училась. Ровно так и получился EOS-баг
(`docs/EOS_INCIDENT.md`).

Тяжёлые импорты при этом ленивые: `import vliw` не требует ни torch, ни
transformers, и без них инструмент работает как раньше — просто без
`/learned`.
