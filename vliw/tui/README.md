# Интерфейс сверху вниз: что менять, что убрать, куда не лезть

Это карта для того, кто хочет переделать вид, а не разбор алгоритма — сам
алгоритм намеренно не описан здесь и не открыт для правок (почему — в конце).
Пользовательское поведение экранов, которые вы увидите ниже, подробно
описано отдельно: [`docs/CODE_MODE.md`](../../docs/CODE_MODE.md) и
[`docs/LAB_MODE.md`](../../docs/LAB_MODE.md) — там про кнопки и жесты, здесь
— про то, где это в коде и что можно перекроить.

## 0. Что это в одном абзаце

Полноэкранное рабочее место на [Textual](https://github.com/Textualize/textual).
Один процесс, один экран приложения (`NexApp`), внутри которого живут четыре
режима-экрана (КОД, РАЗБОР, АГЕНТ, ЯДРО) — Textual называет их «modes», по
одному экземпляру на сессию. Все данные, которые видит интерфейс, уже
посчитаны кем-то другим: экраны только читают и рисуют.

## 1. Карта файлов

```
vliw/tui/
  app.py             NexApp — точка входа, переключение режимов
  bridge.py           мостик к длинным задачам (счёт в фоне, не подвешивая экран)
  palette.py          цветовые роли темы (переменные CSS)
  widgets.py         1738 строк — переиспользуемые виджеты: Panel, Chip,
                      Tool, PanelToolbar, ItemGrid-обёртки, PromptBar
  nex.tcss           1603 строки — вся вёрстка, ни одного инлайн-стиля в коде
  screens/
    base.py           ModeScreen — общий контракт: Esc-лестница, разворот
                       панелей, раскладка по ширине/высоте терминала
    picker.py          экран выбора режима (цифры 1–4)
    code_screen.py    5937 строк — КОД, самый большой файл проекта
    lab_screen.py     3327 строк — РАЗБОР
    core_screen.py    1081 строка — ЯДРО
    agent_screen.py    773 строки — АГЕНТ
```

## 2. Точка входа

`NexApp.__init__` берёт `session`, `execute` (callback на текстовую команду)
и `commands` — всё это собирает `cli.py`, не `tui/`. Дальше `open_mode(name)`
монтирует нужный экран по имени режима (`code`/`lab`/`mind`/`work`) и держит
по одному экземпляру каждого на сессию (`self._modes`). Первым всегда
открывается КОД — остальные режимы равноправными точками входа быть
перестали, к ним уходят из работы (`^O`), не начинают ими. Почему —
комментарий прямо в `app.py` над классом.

## 3. Общий контракт — `base.py`

Все четыре экрана наследуют `ModeScreen`. Он даёт бесплатно:
- лестницу `Esc` (палитра → развёрнутая панель → выход из режима)
- разворот любой панели по 2×клику
- три уровня тесноты по размеру терминала (`.narrow`, `.tight`, `.low`)

Если добавляете новый экран — наследуйте `ModeScreen`, а не пишите раскладку
с нуля: три уровня тесноты уже посчитаны за вас.

## 4. Граница с `vliw/core/` — вот она, дословно

Ни один экран не вызывает планировщик напрямую. Единственное место во всём
проекте, где создаются `GreedyListScheduler`/`OracleScheduler` и зовётся
`.schedule()`, — `Session.results()` в `vliw/cli.py`, **вне** и `core/`, и
`tui/`. Экраны только читают уже посчитанное: `session.dag_obj`,
`session.results()`, готовый объект `Schedule`, и несколько чистых функций
для отображения (`doctor.diagnose`, `dag.compute_metrics`) — ни одна из них
не выбирает расписание, только объясняет то, что уже выбрано.

**Практический вывод.** Хотите новую панель, разворот, тему, раскладку —
дело `tui/`, `session` уже даёт всё нужное. Хотите, чтобы планировщик решал
иначе, — это `core/`, и это другая работа, преднамеренно не описанная здесь.

## 5. Что безопасно менять

- **Цвет и тема** — `palette.py` + `vliw/ui/themes/*.json`. Тема одна на весь
  инструмент: она красит и построчный вывод, и это рабочее место.
- **Вёрстка** — вся в `nex.tcss`, ни одного инлайн-стиля в Python. Найти
  нужный `#id` или `.class` и поменять — не трогая логику экрана.
- **Новая панель на существующем экране** — скопируйте `Panel(...)` с
  тулбаром из `lab_screen.py` (там их семь готовых образцов) и подключите
  чтение из `session`.
- **Новый экран-режим** — наследуйте `ModeScreen`, зарегистрируйте в
  `app.py:open_mode` и в `picker.py`.

## 6. Что можно выкинуть целиком

Режимы независимы друг от друга по конструкции (`_modes` — словарь, не
список с фиксированной длиной). Выкинуть ЯДРО или АГЕНТ как отдельный режим
— значит убрать пункт из `picker.py` и не регистрировать экран в
`app.py:open_mode`; остальные три работать не перестанут. Обратная связь
экранов с `core/` идёт только через `session`, поэтому удаление экрана не
рвёт ничего в логике.

## 7. Куда не лезть, и почему это не забывчивость

`vliw/core/` — сам алгоритм (жадный планировщик, точный поиск) — закрыт для
переделки решением автора, а не потому что не успели описать. Честный
отрицательный результат проекта (обученная модель не обгоняет случайный
перебор на настоящем коде — [`docs/README.md`](../../docs/README.md#журнал-исследования))
измерен на ЭТОЙ конкретной паре planировщиков; менять их без разбора значило
бы незаметно обесценить измерение, на которое ссылается остальная
документация.
