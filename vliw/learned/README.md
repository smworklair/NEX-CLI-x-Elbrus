# vliw/learned — место под будущую обученную модель

Пока здесь **заглушка**. Это зарезервированное место, чтобы, когда обучение на
Hexagon даст рабочую модель планирования широких команд, её можно было
подставить без переделки остального проекта.

## Зачем отдельная папка

Архитектура прототипа разведена по слоям:

```
vliw/
  core/     логика: модель машины, граф, планировщики, метрики, проверка
  ui/       визуализация: цвет, рамки, таблицы, логотип
  learned/  ← ВЫ ЗДЕСЬ: будущая обученная модель
  cli.py    склейка: команда → core → ui → печать
```

`core/`, `ui/` и `cli/` уже ничего не знают про то, откуда взялось расписание —
им важен только контракт `Scheduler`. Значит обученную модель можно вставить
здесь, ничего не трогая снаружи.

## Контракт (протокол `Scheduler` из `vliw/core/api.py`)

Модель — это класс с тремя полями-метками и одним методом:

```python
class LearnedScheduler:
    name  = "ИИ-планировщик (обученная модель)"
    kind  = "learned"      # honestly: baseline=heuristic, oracle=exact, здесь=learned
    short = "learned"

    def schedule(self, dag, model) -> SchedulingResult:
        ...
```

- **вход**: `dag` — граф зависимостей инструкций (`vliw.core.DAG`),
  `model` — модель машины (`vliw.core.MachineModel`: матрица возможностей
  портов, латентности, монопольное занятие);
- **выход**: `SchedulingResult` — ровно тот же тип, что возвращают `baseline`
  и `oracle` (`schedule` с расстановкой инструкций по (такт, порт), плюс
  необязательные `trace`/`notes` для объяснений). За счёт единого типа CLI и UI
  не придётся переделывать.

## Что положить сюда, когда модель появится

1. Веса/чекпойнт обученной модели (или загрузчик к ним).
2. Реализацию `schedule()`: из `dag`+`model` сэмплировать/предсказывать порядок
   и раскладку инструкций, собрать `vliw.core.Schedule`, вернуть
   `SchedulingResult`. Полезно заполнить `trace` (по-тактовые решения) — тогда
   `/explain` и `/compare` покажут её решения так же, как для baseline/oracle.
3. Прогнать `schedule().validate()` — расписание обязано быть законным
   (зависимости, ширина команды, возможности портов, монопольное занятие).

## Как оценивать

Оракул (точный поиск, `vliw/core/oracle.py`) даёт **теоретический потолок** —
недостижимую на практике нижнюю границу по числу тактов. Обученная модель должна
к нему **приближаться**, но оптимума не гарантирует. Метрика качества — тот же
разрыв в тактах, что показывает `compare`/`all`: насколько модель отстаёт от
потолка оракула и насколько обгоняет baseline.

Эталонные расписания для обучения удобно брать у оракула: пары «граф →
оптимальное расписание» на графах, где точный поиск уложился в бюджет.
