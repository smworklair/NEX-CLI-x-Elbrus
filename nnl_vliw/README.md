# nnl_vliw: ядра NNL выбирают группу портфеля крошек

Первая проверка архитектуры NNL (Neural Network Lego) на задаче планировщика VLIW для Эльбруса.
Обучены **два ядра**, в каждом **два блока** (~100 тыс. и ~200 тыс. чисел). Ядра по очереди отвечают на
вопрос «какая самая дешёвая группа портфеля крошек достигает его лучшего результата на этом графе», а потом
проверяют друг друга: если ядра назвали одну группу, берём её, иначе запускаем портфель целиком.

**Короткий итог.** Технически NNL на этой задаче работает: блоки собираются на матплате, проходят линтер
NNL, вставка блока не меняет соседей. По качеству ядра на уровне обычных классификаторов на тех же признаках,
но выбор группы по таким признакам слабый, а перекрёстная проверка ядер **не лучше случайного отказа**.
Для боевого пути (`TinyFastScheduler`) это не нужно, подробности и цифры ниже.

## Как NNL ложится на задачу

- **Композиция одна.** Ядро — матплата с блоками; ответ даёт общий softmax по «ничего» и ответам всех блоков,
  а не независимые мнения блоков. «Ничего» означает «не знаю, запусти портфель целиком».
- **Блоки делят область графа**, а не задачу. Ядро А — по делителям: блок «А_без_делений» (98 659 чисел) и блок
  «А_с_делениями» (196 963). Ядро Б — по памяти: «Б_много_памяти» (98 771) и «Б_мало_памяти» (197 075).
  Область строки считается из графа, ответ блока — «<область>/<группа>».
- **Шина.** Блок пишет на шину понятие своей области, второй блок читает его на такте 2 (так в NNL).
- **Ядро проверяет ядро.** Ядра различаются разбиением, размером вектора токена (48 и 64) и солью хеширования.
- **Язык.** Граф превращается в мешок токенов (`язык.py`): типы операций, критический путь, ресурсная
  граница, ширина, рёбра «А → Б», операции на критическом пути. Язык графу ответа не видит (есть тест).

## Данные и метки

Группы идут от дешёвой к дорогой: `greedy`, `prio`, `defer`, `hold`, `rule`, `beam`. Для каждого графа
`tools/portfolio_labels.py` считает лучший makespan каждой группы (цикл повторяет `TinyScheduler`, 0 расхождений
по итогу). **Метка графа — самая дешёвая группа, достигающая лучшего результата портфеля.**
Верным считается ответ, при котором «жадный + выбранная группа» даёт лучший результат портфеля.

Обучение (64 100 графов из `train_hard`, `train_merged` и 24 000 сгенерированных, без prompt проверочных
наборов): из них **2 502 трудных** (жадного мало). В пул идут все трудные и столько же жадных (5 004 строки:
4 257 в обучение, 747 в dev по группам). Проверка: `eval_hard` (300 графов, 267 трудных), `eval_wide` (300, жадного
всегда хватает) и **настоящие блоки `eval_real`** (947 графов с доказанным оптимумом, 43 трудных).
Обучение идёт только на синтетике, на настоящем коде ядра не видели ничего.

## Что из этого следует

- **NNL-часть работает.** Блоки собираются через Матплату (sha256 проверяется, подмена весов отвергается),
  линтер NNL принимает все четыре, вставка блока другого ядра не меняет ответов соседей на такте 1,
  ответ из сохранённых весов совпадает с прямым проходом обучающего кода.
- **Качество на уровне обычных классификаторов.** По лишним тактам ядро А лучше логрегрессии, бустинга и леса на
  тех же токенах на обоих наборах и при всех сидах; ядро Б примерно на их уровне (на `eval_hard` 118–148 против
  130–176, на `eval_real` 44–46 против 45–46). По макро-точности на dev ядра чуть ниже логрегрессии. Ради качества
  добавлять NNL здесь нет оснований, но и вреда нет.
- **Выбор группы по таким признакам слабый.** Доля верных ответов на dev ~0,37 при шести группах. Признаки
  про конфликты за порты (готовые в один такт, узкие операции) я проверял на тех же классификаторах:
  макро-точность не выросла (0,39 → 0,40), в язык они не вошли.
- **На настоящем коде почти нет эффекта.** Из 947 графов жадного не хватает на 43, и ядра, обученные на
  синтетике, возвращают меньше пятой части этих 47 тактов (ядро А: 6–9). Из 382 трудных синтетических графов
  выборки без деления только 3, а у настоящего кода 37 из 43 трудных без деления: это сдвиг распределения.
- **Перекрёстная проверка не работает как сигнал ошибки.** При согласии ядро А право в 62 % случаев на
  `eval_hard`, при расхождении в 77 % (сид 1); по тактам перекрёсток хуже случайного отказа в 5 из 6 случаев
  (два набора × три сида), см. таблицы. Отказ по уверенности одного ядра (кривая в выводе `оценка.py`) держится
  примерно на уровне случайного отказа.

## Ограничения

- Группы портфеля частично взаимозаменяемы (`beam`, `rule`, `prio` часто достигают одного результата), метка
  «самая дешёвая» зависит от порядка групп. Это шум метки, а не ошибка ядер.
- Только три сида, один набор настоящих блоков (25 файлов lcc), 43 трудных на настоящем коде. Модельные
  такты, не железо; `loop_mode` не моделируется.
- Дёшево ли ядро по времени, не измерялось: проверялось только качество выбора.
- Метки обучения не лежат в репозитории (десятки МБ); повторный запуск даст ту же картину, но не те же цифры
  до последнего знака (разбиение зависит от порядка строк).

## Воспроизведение

```bash
# 1. метки проверочных наборов и обучающих графов
python3 tools/portfolio_labels.py eval_hard.jsonl eval_wide.jsonl eval_real.jsonl --out labels/
python3 tools/portfolio_labels.py train_hard.jsonl train_merged.jsonl --unique --out labels/ \
    --exclude eval_hard.jsonl,eval_hard_dev.jsonl,eval_wide.jsonl,eval_real.jsonl
python3 tools/gen_graphs.py --n 24000 --out labels/train_gen.jsonl
python3 tools/portfolio_labels.py labels/train_gen.jsonl --out labels/
# 2. обучение и оценка (секунды на CPU)
python3 -m nnl_vliw.обучить --метки labels/ --выход /tmp/блоки --зерно 1
python3 -m nnl_vliw.оценка  --метки labels/ --блоки /tmp/блоки --json /tmp/оценка.json
python3 -m nnl_vliw.база_sklearn --метки labels/      # нужен scikit-learn
# 3. проверка блоков из репозитория линтером NNL
python3 nnl_vliw/NNL/линтер.py nnl_vliw/блоки/А/А_с_делениями nnl_vliw/архитектуры
python3 -m unittest tests.test_nnl_vliw
```

## Что дальше

Если продолжать, то менять нужно **признаки и задачу**, а не архитектуру: по токенам-мешку выбор группы
упирается в потолок ~0,4. Варианты: покомандные признаки крошек (`vliw/tiny/features.py`) вместо мешка;
другая задача для ядер (например, «достигнута ли нижняя граница», что близко к «не знаю» в NNL); больше
настоящих трудных примеров (больше файлов lcc). Быстрый путь уже есть: `TinyFastScheduler` даёт тот же результат,
что портфель, за ~1 мс на граф настоящего кода (см. `docs/TINY_FAST.md`).
