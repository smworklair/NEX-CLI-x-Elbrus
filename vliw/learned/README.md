# vliw/learned — обученная модель как планировщик

Заглушки здесь больше нет — модель обучена (LoRA поверх Qwen2.5-3B, веса на
[Hugging Face](https://huggingface.co/Shmonika/nex-vliw-lora)) и запускается
из CLI командой `/learned` (`vliw/learned/scheduler.py` реализует протокол
`Scheduler`, инференс — в `runtime.py`). Что реально показал замер — раздел
«Как оценивать» ниже: результат честный и отрицательный.

## Зачем отдельная папка

Архитектура прототипа разведена по слоям:

```
vliw/
  core/     логика: модель машины, граф, планировщики, метрики, проверка
  ui/       визуализация: цвет, рамки, таблицы, логотип
  learned/  ← ВЫ ЗДЕСЬ: будущая обученная модель
  cli.py    склейка: команда → core → ui → печать
```

`core/`, `ui/` и `cli/` уже ничего не знают про то, откуда взялось расписание —
им важен только контракт `Scheduler`. Значит обученную модель можно вставить
здесь, ничего не трогая снаружи.

## Контракт (протокол `Scheduler` из `vliw/core/api.py`)

Модель — это класс с тремя полями-метками и одним методом:

```python
class LearnedScheduler:
    name  = "ИИ-планировщик (обученная модель)"
    kind  = "learned"      # honestly: baseline=heuristic, oracle=exact, здесь=learned
    short = "learned"

    def schedule(self, dag, model) -> SchedulingResult:
        ...
```

- **вход**: `dag` — граф зависимостей инструкций (`vliw.core.DAG`),
  `model` — модель машины (`vliw.core.MachineModel`: матрица возможностей
  портов, латентности, монопольное занятие);
- **выход**: `SchedulingResult` — ровно тот же тип, что возвращают `baseline`
  и `oracle` (`schedule` с расстановкой инструкций по (такт, порт), плюс
  необязательные `trace`/`notes` для объяснений). За счёт единого типа CLI и UI
  не придётся переделывать.

## Что сделано (не план — уже реализовано)

1. Веса обучены и опубликованы: три адаптера (`qwen-vliw-lora`, `lora-merged`,
   `lora-eos`) на Hugging Face, история обучения — в `docs/JOURNAL.md`.
2. `schedule()` реализован: `(dag, model)` кодируется в промпт
   (`training.encode.encode_prompt`), модель генерирует продолжение,
   `decode_completion` собирает `Schedule`. Если ответ невалиден —
   планировщик честно откатывается на `baseline`, а не выдаёт сломанное
   расписание как рабочее (см. докстринг `scheduler.py`).
3. `trace` заполняется — `/explain` и `/compare` показывают решения модели
   так же, как для baseline/oracle.

## Как оценивать — и что показал реальный замер

Оракул (точный поиск, `vliw/core/oracle.py`) даёт **теоретический потолок**.
На синтетических графах, на которых модель обучалась, она обгоняет baseline
на части случаев (детали — `docs/CAB.md`, `docs/JOURNAL.md`). Но это не
главный результат: на **настоящем коде** после `lcc` (графы 112–386 узлов,
вне распределения обучения) модель проверена против случайного перебора и
не обошла его ни на одном из 13 графов, суммарно +0 тактов — методика,
`VERIFY.sh` и сырые данные лежат в
[`real_candidates_100_400/model_eval/`](../../real_candidates_100_400/model_eval/REPORT.md).
Разница между этими двумя результатами — не противоречие, а разница
условий: синтетика внутри распределения обучения против настоящего кода
вне его. Обе цифры настоящие, ни одна не отменяет другую.
