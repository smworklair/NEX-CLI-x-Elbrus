# Настоящий код против синтетики: что показал компилятор

Снято 29.08.2026. Всё воспроизводится локально одной командой, без GPU и без
доступа к железу:

```bash
python3 tools/check_real_vs_synth.py
```

## Откуда числа

Кросс-`lcc` 1.29.16 из свободного комплекта МЦСТ уже лежит в
`~/e2k-toolchain` — им же сняты `examples/probes/`. Инструмент компилирует
им пять обычных C-программ (цикл с накоплением, плавающая точка, ветвление,
копирование памяти, хеш строки) на `-O0/-O2/-O3` и разбирает результат тем
же парсером, что и весь проект.

**Кросс-компилятор репрезентативен.** Тот же цикл скомпилирован настоящим
`lcc` на машине e2k по SSH: 49 операций против 50, список незнакомых
мнемоник совпал полностью. Для вопроса «похож ли настоящий код на нашу
синтетику» доступ к железу не нужен.

## Главное: словари не пересекаются там, где это важно

Обучающая выборка — восемь целочисленных классов:

| файл | графы | классы |
|---|---|---|
| `dataset.jsonl` | 6..14 | ADD 28% · MUL 22% · LOAD 14% · SUB 14% · AND 7% · SHL 7% · DIV 7% |
| `train_merged.jsonl` | 4..24 | ADD 27% · MUL 16% · SUB 15% · LOAD 14% · AND 10% · SHL 9% · DIV 5% · STORE 4% |

Настоящий вывод компилятора: **37% операций в графе получают класс
UNKNOWN** — мнемоники, которых в словаре нет вовсе. Это не экзотика по
краям, а то, чем e2k является:

- `cmpesb`, `cmplsb`, `cmpandesb`, `landp`, `pass` — вычисление предикатов,
  то есть **if-conversion**, центральный механизм VLIW;
- `qpaddw`, `qppackdl`, `qpswitchd`, `paddw` — упакованный SIMD;
- `aaurw`, `aaurwd`, `fapb` — устройство доступа к массивам, аппаратная
  предподкачка цикла, фирменная черта Эльбруса;
- `faddd`, `fsubd`, `fmuld`, `fdivd` — плавающая точка целиком. На программе
  с `double` незнакомых **100%** на любом уровне оптимизации.

И обратно: `DIV` занимает 3-7% обучающей выборки, а в настоящем выводе не
встретился **ни разу**.

Размеры тоже расходятся: синтетика 4..24 операции, однострочный `memcpy` на
`-O3` даёт 112.

## Оговорка, без которой числа читаются неверно

`UNKNOWN` — заглушка: латентность 1, любой канал. Расписание, посчитанное по
ней, физике не соответствует — `fdivd` не исполняется за такт. Смысл класса
в том, что теперь это **видно в каждом отчёте**, а не спрятано под ADD, как
было раньше (см. коммит про три места, где парсер молча врал). Верными числа
делает только пополнение `MNEMONICS` настоящими классами с замером портов
через `probe_matrix.py` — это недели, не часы.

Пока этого нет, любой вывод про настоящий код читается так: «структура
графа — примерно, времена — нет».

## Что из этого следует

Развилка, которую стоит решать явно, а не по умолчанию:

1. **Сузить заявку.** Проект планирует расписания для целочисленного
   ALU-подмножества e2k. Тогда текущие данные валидны, а формулировка
   «планировщик для e2k» в README требует оговорки.
2. **Расширить словарь** — предикаты, SIMD, AAU, плавающая точка. Единственный
   путь к верным числам на настоящем коде, но требует снять матрицу портов
   для новых классов.
3. **Учить на выводе `lcc`** вместо синтетики. Компилятор локальный, данных
   можно сделать сколько угодно, `compiler_schedule()` даёт готовый эталон.
   Но эталон тогда — решение lcc, а не доказанный оптимум CP-SAT, и сравнение
   «мы против компилятора» теряет смысл: учиться у него и обыгрывать его
   одновременно нельзя.

Прогон 3 к этой развилке отношения не имеет: обучающие данные порождает
`tools/vliw_gen.py` через CP-SAT, парсер ассемблера он не импортирует вовсе.
Ветки независимы, и «сначала одно, потом другое» — вопрос приоритета, а не
зависимости.
